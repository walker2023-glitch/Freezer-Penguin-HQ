## 1. System Context & Local Stack

### 1.1 Runtime Environment

The Freezer Penguin backend is a **Python FastAPI** application served by **Uvicorn** in a local development context. The application communicates with a remote **MySQL 8.0.46** instance through a **Tailscale mesh VPN tunnel**. The database host is reachable exclusively at the private Tailscale IP `100.81.95.123`. No direct public internet route to the MySQL instance exists or should ever be created.

## 2. System-Wide Guardrails

These rules are non-negotiable constraints on database schema design and ORM modeling. Any code, migration, or AI-generated output that violates a guardrail MUST be rejected and corrected before merging.

### GR-1 — UPC Column MUST Remain Nullable

**Rule:** The `UPC` / `upc` column in `inventory_items` (and its corresponding SQLAlchemy ORM attribute) MUST be declared `nullable=True` at all times. This column MUST NEVER be set to `NOT NULL`, `nullable=False`, or marked as a required field in any Pydantic schema.

**Rationale:** Raw leftover items entered via image ingestion (Feature 1.2 — Gemini Vision) have no associated barcode. Forcing `NOT NULL` on `upc` would make it impossible to log any non-packaged food item, destroying the core value proposition of the application. The nullable FK relationship between `inventory_items.UPC` and `barcode_master.UPC` is intentional and architecturally sound.

**Correct SQLAlchemy declaration:**
```python
upc = Column(String(15), nullable=True, index=True)
```

**Correct Pydantic v2 declaration:**
```python
upc: Optional[str] = Field(None, description="12-digit UPC barcode string")
```

**Violation examples that MUST NOT appear:**
```python
# FORBIDDEN
upc = Column(String(15), nullable=False)
upc: str = Field(...)
```

---

### GR-2 — All Application-Level Primary Keys MUST Use Single Auto-Increment Isolation

**Rule:** Every SQLAlchemy ORM model MUST define exactly one column as its `primary_key=True` with `autoincrement=True`. Composite primary keys are NOT to be introduced in new ORM models or new migration DDL. Where composite PKs already exist in the live DDL (`inventory_items`, `storage_locations`), the application layer MUST treat only the auto-increment column (`item_id`, `location_id`) as the functional PK for all query, insert, and response operations.

**Rationale:** Composite PKs in SQLAlchemy create mapping ambiguity, complicate `session.get()` lookups, and produce inconsistent Pydantic serialization when the response model references a single `id` field. The existing composite PKs in `inventory_items` (`item_id + user_id + unit_id`) and `storage_locations` (`location_id + user_id`) are acknowledged legacy DDL artifacts. All new ORM code must route around this by using the auto-inc column exclusively.

**Correct pattern:**
```python
class DBInventoryItem(Base):
    __tablename__ = "inventory_items"
    item_id = Column(Integer, primary_key=True, index=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("Users.user_id"), nullable=False)
    # ...
```

**Permitted exception:** `recipe_ingredients_has_recipes` — pure junction table where a composite PK of `(map_id, recipe_id)` is correct and acceptable.

## 3. System Context & Code Patterns

All backend code generated, reviewed, or modified by AI agents or contributors MUST conform to the following patterns. These patterns enforce consistency, correctness, and maintainability across the codebase.

### 3.1 Pydantic v2 Data Serialization Models

**Rule:** All request and response schemas MUST be implemented as Pydantic `BaseModel` subclasses using Pydantic v2 syntax. The following conventions are mandatory:

- **FR-3.1.1** Field definitions MUST use `Field(...)` with explicit `description` and `json_schema_extra={"example": ...}` for every public-facing field.
- **FR-3.1.2** Optional fields MUST use `Optional[T]` with a `None` default — never `T | None` without a default.
- **FR-3.1.3** All response models (models that serialize database ORM objects) MUST include `model_config = ConfigDict(from_attributes=True)` or the equivalent `class Config: from_attributes = True`. This is required for SQLAlchemy ORM → Pydantic serialization compatibility.
- **FR-3.1.4** A three-tier schema hierarchy MUST be maintained: `{Entity}Base` (shared fields) → `{Entity}Create` (inbound write payload) → `{Entity}Response` (outbound serialized record with DB-generated fields like `id` and `timestamp`).
- **FR-3.1.5** Numeric validation constraints (e.g., `ge=1`) MUST be expressed inside `Field()`, not as a `@validator` or `@field_validator` unless the logic cannot be expressed as a field constraint.

**Canonical pattern:**
```python
from pydantic import BaseModel, Field
from typing import Optional
from datetime import datetime

class InventoryItemBase(BaseModel):
    name: str = Field(..., description="Food item name", json_schema_extra={"example": "Wild Caught Salmon"})
    quantity: int = Field(default=1, ge=1, description="Item count (minimum 1)", json_schema_extra={"example": 2})
    storage_zone: str = Field(..., description="Physical storage location", json_schema_extra={"example": "Kitchen Freezer"})
    upc: Optional[str] = Field(None, description="12-digit UPC barcode string", json_schema_extra={"example": "012345678912"})
    notes: Optional[str] = Field(None, description="Optional item notes")

class InventoryItemCreate(InventoryItemBase):
    pass

class InventoryItemResponse(InventoryItemBase):
    id: int = Field(..., description="Auto-increment database primary key")
    timestamp: datetime = Field(..., description="Server-generated creation timestamp")

    class Config:
        from_attributes = True
```

### 3.2 Explicit Route Status Responses

**Rule:** Every FastAPI route MUST declare an explicit `status_code` using `fastapi.status` constants. Relying on the default `200 OK` for write operations is FORBIDDEN.

| HTTP Method | Required Status Code | Constant |
|---|---|---|
| `POST` (create) | 201 Created | `status.HTTP_201_CREATED` |
| `GET` (retrieve) | 200 OK | `status.HTTP_200_OK` |
| `PUT` / `PATCH` (update) | 200 OK | `status.HTTP_200_OK` |
| `DELETE` (remove) | 204 No Content | `status.HTTP_204_NO_CONTENT` |
| Resource not found | 404 Not Found | raise `HTTPException(status_code=404)` |
| External API unavailable | 503 Service Unavailable | raise `HTTPException(status_code=503)` |
| Duplicate / conflict | 409 Conflict | raise `HTTPException(status_code=409)` |

**Canonical route declaration pattern:**
```python
from fastapi import APIRouter, status, Depends, HTTPException
from sqlalchemy.orm import Session
from app.database import get_db
from app.schemas import InventoryItemCreate, InventoryItemResponse

router = APIRouter(prefix="/inventory", tags=["Inventory"])

@router.post(
    "/barcode/{upc}",
    response_model=InventoryItemResponse,
    status_code=status.HTTP_201_CREATED,
    summary="Lookup UPC via Open Food Facts and persist to inventory",
)
async def ingest_barcode_item(upc: str, db: Session = Depends(get_db)):
    ...
```

### 3.3 SQLAlchemy Contextual Session Handling

**Rule:** All database write operations MUST be wrapped in a `try/except/rollback` block. Session lifecycle is managed by the `get_db()` dependency injector in `database.py`. Manual session instantiation outside of `get_db()` is FORBIDDEN in router or service code.

**Mandatory session pattern for all write operations:**
```python
def create_inventory_item(db: Session, item_data: InventoryItemCreate) -> DBInventoryItem:
    db_item = DBInventoryItem(**item_data.model_dump())
    try:
        db.add(db_item)
        db.commit()
        db.refresh(db_item)
        return db_item
    except Exception as exc:
        db.rollback()
        logger.error("DB write failed during inventory insert: %s", exc)
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail="Database write operation failed. Transaction rolled back."
        )
```

**`get_db()` canonical definition (already implemented in `database.py`):**
```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

- `autocommit=False` and `autoflush=False` MUST remain set on `SessionLocal`.
- `db.refresh(db_item)` MUST be called immediately after `db.commit()` on create operations to return server-generated values (`item_id`, `timestamp`) in the response.
- Reads (SELECT-only routes) do NOT require `try/except/rollback` but MUST still use the `get_db()` dependency.

### 3.4 Outbound HTTP Calls (Open Food Facts / External APIs)

**Rule:** All outbound HTTP calls MUST use `httpx.AsyncClient` with an explicit timeout. Blocking `requests` library calls are FORBIDDEN in async route handlers.

```python
import httpx
import logging

logger = logging.getLogger(__name__)

async def lookup_upc(upc: str) -> dict:
    url = f"https://world.openfoodfacts.org/api/v0/product/{upc}.json"
    headers = {"User-Agent": "FreezerPenguin/1.0"}
    try:
        async with httpx.AsyncClient(timeout=10.0) as client:
            response = await client.get(url, headers=headers)
            response.raise_for_status()
            data = response.json()
            logger.info("OFF API responded with status=1 for UPC=%s", upc)
            return data
    except httpx.TimeoutException:
        logger.warning("OFF API timeout for UPC=%s", upc)
        raise HTTPException(status_code=503, detail="Open Food Facts API unavailable. Please try again later.")
    except httpx.HTTPStatusError as exc:
        logger.warning("OFF API returned non-2xx status=%s for UPC=%s", exc.response.status_code, upc)
        raise HTTPException(status_code=503, detail="Open Food Facts API unavailable. Please try again later.")
```

- `timeout=10.0` seconds is the MAXIMUM permitted. Do not increase this value.
- The `User-Agent: FreezerPenguin/1.0` header MUST be sent per Open Food Facts API etiquette.
- All response fields parsed from the OFF payload MUST use `.get()` with `None` as the default — never direct key access. The OFF schema is sparse and inconsistent.

## 4. Error Handling & Observability

### 4.1 Logging Mandate

**Rule:** Every operation that touches the database or an external API MUST emit a structured log line via Python's standard `logging` module. `print()` statements are FORBIDDEN in production code paths.

**Mandatory log coverage:**

| Event | Log Level | Required Fields |
|---|---|---|
| Successful DB INSERT | `INFO` | table name, primary key value, user context |
| Successful external API call | `INFO` | service name, identifier (UPC/item_id), HTTP status code |
| API response not found (404 condition) | `WARNING` | service name, identifier, response status |
| API timeout or 5xx | `WARNING` | service name, identifier, exception message |
| DB write failure / rollback | `ERROR` | table name, exception message, transaction state |
| Startup / DB connection validation | `INFO` | DATABASE_URL host (masked), engine status |
| Request received on ingestion routes | `INFO` | route path, inbound identifier (UPC, item_id) |

**Module-level logger initialization (required at top of every module that performs I/O):**
```python
import logging
logger = logging.getLogger(__name__)
```

**Example compliant log sequence for a barcode ingestion operation:**
```

INFO:     app.services_open_food_facts: OFF API responded with status=1 for UPC=012345678912
INFO:     app.routers_inventory: DB INSERT complete — inventory_items.item_id=42 for UPC=012345678912

```

**Rule:** All client-facing error responses MUST use `fastapi.HTTPException` with a `detail` string that is human-readable and machine-parseable by the Flutter client. Unhandled exceptions that bubble to the ASGI layer are a MAJOR defect.

### 4.4 ai_audit_logs Write Contract

**Rule:** Every AI inference call (Gemini Vision — Feature 1.2; Recipe Engine — Feature 1.3) MUST write a corresponding row to `ai_audit_logs` containing:
- `input_prompt`: The full prompt string sent to the model
- `raw_output`: The verbatim model response string

This write MUST occur **after** the primary business write (inventory insert, recipe cache write) succeeds. `ai_audit_logs` writes MUST be fire-and-forget (failures MUST NOT roll back the primary transaction) but MUST emit an `ERROR` log if the audit write itself fails.

## 5. Functional Requirements Summary

Numbered, testable requirements derived from the full feature scan. Written in RFC 2119 form.

- **FR-1.** The system MUST accept `DATABASE_URL` exclusively from `backend/.env` and MUST raise `RuntimeError` at startup if the variable is absent.
- **FR-2.** The system MUST initialize all SQLAlchemy ORM tables via `Base.metadata.create_all(bind=engine)` at application startup.
- **FR-3.** The `upc` column in all ORM models and Pydantic schemas that reference `inventory_items` MUST be `Optional[str]` / `nullable=True`. This rule MUST survive all future schema migrations.
- **FR-4.** All new SQLAlchemy ORM models MUST define a single auto-increment integer column as the sole `primary_key=True`. Composite PKs MUST NOT be introduced in new models.
- **FR-5.** All `POST` routes that create a new database record MUST return `HTTP 201 Created`.
- **FR-6.** All database writes MUST be wrapped in `try/except` with `db.rollback()` on the exception path and a subsequent `raise HTTPException`.
- **FR-7.** All outbound API calls MUST use `httpx.AsyncClient` with `timeout=10.0`. The `requests` library MUST NOT be used in async route handlers.
- **FR-8.** Every module that performs I/O (database or HTTP) MUST initialize a module-level logger via `logging.getLogger(__name__)` and emit `INFO`-level confirmation on success and `WARNING` or `ERROR` on failure.
- **FR-9.** All parsed fields from external API responses (Open Food Facts, Spoonacular) MUST use `.get()` with `None` as the default. Direct key access (`response["field"]`) is FORBIDDEN on external API payloads.
- **FR-10.** The `barcode_master` table MUST be treated as a read-only reference catalog in application code. No application route may INSERT or UPDATE rows in `barcode_master` directly.
- **FR-11.** The `ai_audit_logs` table MUST receive an append-only INSERT for every AI inference event. It MUST NOT be queried, updated, or deleted by application code.
- **FR-12.** The system SHOULD respond to barcode ingestion requests within 3 seconds under normal network conditions.

## 6. Non-Functional Requirements

- **Performance** — Barcode ingestion (`POST /api/v1/inventory/barcode/{upc}`) MUST respond p95 ≤ 3s. The OFF `httpx` client timeout cap of 10s prevents tail-latency runaway. SQLAlchemy queries on `inventory_items` MUST use the indexed `UPC` and `item_id` columns in WHERE clauses.
- **Security** — No credentials, IPs, or API keys are to be hardcoded in any Python file. All secrets MUST live in `backend/.env`. The `backend/.env` file MUST be listed in `.gitignore`. The Tailscale VPN is the sole permitted network path to MySQL.
- **Reliability** — All write operations MUST be transactional. Partial writes (committed header, uncommitted FK rows) are a BLOCKER defect. `autocommit=False` on `SessionLocal` is non-negotiable.
- **Observability** — Uvicorn stdout MUST surface: inbound request identifiers (UPC, item_id), external API response codes, DB write confirmations (with resulting PKs), and all failure events with exception messages.
- **Maintainability** — Service logic (HTTP clients, data parsing) MUST reside in `services_*.py` modules. Route handlers MUST be thin orchestrators: validate → call service → write DB → return response. No business logic in `main.py`.
- **Backward Compatibility** — Existing `inventory_items` rows (504 auto-inc value observed) MUST not be disturbed by ORM model changes. All migrations MUST be additive. No `DROP COLUMN` or `NOT NULL` constraint additions without an explicit backfill strategy.

## 7. Acceptance Criteria

- **AC-1.** *Given* a valid known UPC, *when* `POST /api/v1/inventory/barcode/{upc}` is called, *then* the system returns HTTP `201` with a JSON body containing `item_id`, `upc`, and `created_at`, and a new row is visible in `inventory_items`.
- **AC-2.** *Given* an unknown UPC, *when* the barcode endpoint is called, *then* the system returns HTTP `404` with `{"detail": "Product not found in Open Food Facts for UPC: {upc}"}` and zero rows are written to the database.
- **AC-3.** *Given* any database write operation, *when* a SQLAlchemy exception is raised mid-transaction, *then* `db.rollback()` is called, the transaction is fully reversed, an `ERROR` log is emitted to Uvicorn stdout, and the client receives a `500` response.
- **AC-4.** *Given* a raw leftover item with no barcode, *when* a record is inserted into `inventory_items` with `upc=NULL`, *then* the insert MUST succeed without constraint violation.
- **AC-5.** *Given* application startup with a missing `DATABASE_URL`, *when* `uvicorn app.main:app` is executed, *then* the process exits with a `RuntimeError` before accepting any HTTP connections.
- **AC-6.** *Given* any successful inventory insert, *when* the Uvicorn log stream is observed, *then* a structured `INFO` log line is present showing the resulting `item_id` and the input identifier (UPC or vision session ID).
- **AC-7.** *Given* the `/docs` Swagger UI, *when* any POST endpoint is executed manually, *then* the response body matches the declared Pydantic `response_model` exactly, with all `Optional` fields serializing as `null` (not omitted) when absent.

## 10. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `upc` column set to `NOT NULL` by mistake during ORM refactor | Medium | High | GR-1 enforces `nullable=True`; AC-4 tests null insert |
| Composite PK in new ORM model breaks `session.get()` lookups | Medium | High | GR-2 mandates single auto-inc PK on all new models |
| SQLAlchemy session left open after exception | Low | High | GR-3.3 mandates `try/except/rollback` on all writes |
| `DATABASE_URL` accidentally committed to git | Low | Critical | GR-3 + `.gitignore` enforcement |
| OFF API field schema changes break response parser | Low | Medium | All OFF fields accessed via `.get(None)`; isolated in `services_open_food_facts.py` |
| Uvicorn log noise from SQLAlchemy `echo=True` in prod | Low | Low | `echo=False` is the default; document as dev-only toggle |
| `barcode_master` table mutation corrupts product catalog | Low | High | FR-10 enforces read-only access policy at application layer |
