## 1. Problem Statement

The existing Open Food Facts barcode lookup logic is isolated in a root-level legacy script (`main.py`) and was written as a standalone `httpx` prototype with no database write capability. This script cannot be used by the FastAPI application layer, cannot be tested via the `/docs` Swagger UI, and does not integrate with the 11-table MySQL schema. Without a proper router-level implementation, no other ingestion or recipe feature can reliably assume that product data exists in the database. Migrating this logic is the critical path that unblocks all downstream inventory features.

---

## 2. Goals

- Encapsulate the Open Food Facts API call inside a dedicated `httpx`-powered async service module (`services/open_food_facts.py`).
- Expose the lookup-and-persist flow as a clean `POST /inventory/barcode/{upc}` FastAPI route inside `routers/inventory.py`.
- Write the parsed product result to the correct MySQL table(s) via SQLAlchemy, respecting all schema constraints (nullable `UPC`, `item_id` auto-increment PK).
- Return a well-typed Pydantic v2 response confirming the saved record.
- Surface graceful, observable HTTP error codes for all known failure modes (unknown UPC, API timeout, duplicate entry).

---

## 3. Non-Goals

- This feature does NOT implement a barcode camera scanner or any mobile/UI scanning interface.
- This feature does NOT handle image-based item recognition (reserved for Feature 1.2).
- This feature does NOT cache Open Food Facts responses in Redis or any external store — a direct DB write is the sole persistence mechanism at this stage.
- This feature does NOT implement batch/bulk barcode ingestion.
- This feature does NOT modify or delete existing inventory records (upsert is out of scope; insert-only for now).

---

## 4. Personas & User Stories

- **As a User**, I want to scan a product's barcode so that its nutritional and product metadata is automatically populated in my freezer inventory without manual data entry.
- **As a Developer**, I want the barcode lookup to live inside `backend/app/routers/` so that I can test it end-to-end via Swagger UI and confirm the database write in MySQL.
- **As a System**, I want all failed lookups (unknown UPC, API errors) to return structured error responses so that the client application can display meaningful feedback to the user.

---

## 5. Functional Requirements

- **FR-1.** The system MUST accept a UPC barcode value as a path parameter via `POST /inventory/barcode/{upc}`.
- **FR-2.** The system MUST query the Open Food Facts REST API (`https://world.openfoodfacts.org/api/v0/product/{upc}.json`) using an async `httpx.AsyncClient`.
- **FR-3.** The system MUST parse the Open Food Facts response and extract at minimum: product name, brand, categories, nutriscore grade, image URL, and quantity/unit.
- **FR-4.** The system MUST persist the parsed product data to the correct MySQL table via a SQLAlchemy `Session`, with `UPC` stored as the provided barcode string.
- **FR-5.** The system MUST return HTTP `201 Created` with a serialized Pydantic v2 response body representing the newly inserted record.
- **FR-6.** The system MUST return HTTP `404 Not Found` if the Open Food Facts API returns a `product_found: 0` or an empty product object for the given UPC.
- **FR-7.** The system MUST return HTTP `503 Service Unavailable` if the Open Food Facts API is unreachable or returns a non-2xx status code, and MUST NOT write any partial data to the database in this case.
- **FR-8.** The system SHOULD log each successful DB write at `INFO` level and each API failure at `WARNING` level via Python's standard `logging` module, visible in Uvicorn output.
- **FR-9.** The system MUST use dependency-injected SQLAlchemy `Session` (via `get_db()`) — no global session state.

---

## 6. Non-Functional Requirements

- **Performance:** The endpoint SHOULD respond within 3 seconds under normal network conditions. The `httpx` client MUST be configured with a `timeout=10.0` seconds to prevent hanging requests.
- **Security:** The Open Food Facts API is public and requires no API key. No credentials are stored. All database credentials MUST remain in `backend/.env` and be loaded via `python-dotenv` / `pydantic-settings`. No secrets are to be hardcoded.
- **Observability:** Uvicorn stdout MUST display: (1) the incoming UPC, (2) the Open Food Facts HTTP status code received, (3) confirmation of the DB `INSERT` with the resulting `item_id`, or (4) the specific failure reason if the write does not occur.

---

## 7. Acceptance Criteria

- **AC-1.** Given a valid, known UPC (e.g., `0021130126026`), when `POST /inventory/barcode/0021130126026` is called, then the system returns HTTP `201` with a JSON body containing the `item_id` of the newly created record, the product name, and the stored `upc` value.
- **AC-2.** Given an unknown or unrecognized UPC, when the endpoint is called, then the system returns HTTP `404` with a JSON body `{"detail": "Product not found in Open Food Facts for UPC: {upc}"}` and no database row is created.
- **AC-3.** Given a successful product lookup, when the record is written to MySQL, then the `upc` column stores the barcode string, nullable fields that are absent from the OFF response store `NULL`, and the `item_id` is auto-assigned by the database.
- **AC-4.** Given the Open Food Facts API is unreachable or returns a 5xx error, when the endpoint is called, then the system returns HTTP `503` with `{"detail": "Open Food Facts API unavailable. Please try again later."}` and performs zero database writes.
- **AC-5.** Given any outcome (success or failure), when Uvicorn processes the request, then a structured log line appears in stdout identifying the UPC, the OFF response status, and the final outcome of the DB operation.
- **AC-6.** Given the `/docs` Swagger UI, when a developer manually inputs a UPC and executes the endpoint, then the full round-trip (API call → DB write → 201 response) completes without unhandled exceptions.

## 8. Data Model

**Primary Table Affected:** The inventory items table (maps to the SQLAlchemy model representing manufactured/packaged food products).

**Columns Written By This Feature:**

| Column | Type | Nullable | Source |
|---|---|---|---|
| `item_id` | `INT` AUTO_INCREMENT PK | No | DB-generated |
| `upc` | `VARCHAR(14)` | **YES** | Path parameter `{upc}` |
| `product_name` | `VARCHAR(255)` | Yes | OFF → `product.product_name` |
| `brand` | `VARCHAR(255)` | Yes | OFF → `product.brands` |
| `categories` | `TEXT` | Yes | OFF → `product.categories` |
| `nutriscore_grade` | `CHAR(1)` | Yes | OFF → `product.nutriscore_grade` |
| `image_url` | `TEXT` | Yes | OFF → `product.image_url` |
| `quantity` | `VARCHAR(50)` | Yes | OFF → `product.quantity` |
| `created_at` | `DATETIME` | No | Server-side `DEFAULT CURRENT_TIMESTAMP` |

**Constraints:**
- All PKs use `item_id` auto-increment style. No composite keys.
- `UPC` is explicitly `Nullable` — this column must never be set to `NOT NULL` in the ORM model.

## 9. API Surface

**Route:** `POST /inventory/barcode/{upc}`

**Path Parameter:**
```
upc: str  — The 8, 12, or 13-digit UPC/EAN barcode string
```

**Request Body:** None — the UPC is passed as a path parameter only.

**Success Response — HTTP 201:**
```json
{
  "item_id": 42,
  "upc": "0021130126026",
  "product_name": "Organic Whole Milk",
  "brand": "Horizon Organic",
  "categories": "Dairy, Milk",
  "nutriscore_grade": "b",
  "image_url": "https://images.openfoodfacts.org/...",
  "quantity": "1 gal",
  "created_at": "2025-01-15T10:32:00"
}
```

**Error Response — HTTP 404:**
```json
{
  "detail": "Product not found in Open Food Facts for UPC: 9999999999999"
}
```

**Error Response — HTTP 503:**
```json
{
  "detail": "Open Food Facts API unavailable. Please try again later."
}
```

- **Open Food Facts API (External)**

  - Auth: None required (public API)
  - Client: `httpx.AsyncClient` with `timeout=10.0`

  - Rate limits: Generous; no throttling expected at development scale. Add `User-Agent: FreezerPenguin/1.0` header per OFF API etiquette.

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Open Food Facts returns incomplete/missing fields for a valid UPC | High | Low | All parsed fields are `Optional` in the Pydantic schema; missing fields write as `NULL`. Never raise on absent keys. |
| UPC already exists in the database (duplicate scan) | Medium | Medium | Return HTTP `409 Conflict` with the existing `item_id`. Do not overwrite. Implement check before INSERT. |
| httpx request hangs indefinitely | Low | High | `timeout=10.0` enforced on `AsyncClient`. `asyncio.TimeoutError` caught and mapped to `503`. |
| Open Food Facts API schema changes break parser | Low | Medium | Access all fields via `.get()` with `None` defaults. Field extraction is isolated in `services/open_food_facts.py` — single location to patch. |
| SQLAlchemy session left open on exception path | Low | High | Use `try/except/finally` with explicit `db.rollback()` on failure, scoped inside the dependency-injected session. |

## 18. Open Questions

- **Q1:** Does the live MySQL schema use a single unified `items` table for both barcode-scanned products (Feature 1.1) and image-recognized leftovers (Feature 1.2), or are they split into separate tables? The answer determines whether one SQLAlchemy model or two are needed before writing any ORM code.
- **Q2:** Should the `created_at` timestamp be set application-side (`datetime.utcnow()`) or rely on the MySQL `DEFAULT CURRENT_TIMESTAMP`? Keeping it DB-side is preferred for consistency but requires confirming the column default is set in the live schema.
- **Q3:** What is the agreed-upon behavior when a UPC is submitted that already exists? The risk table assumes `409 Conflict`, but the product may have been updated upstream (e.g., new image URL). An optional `?force=true` query param for overwrite is a future consideration but is out of scope here.
