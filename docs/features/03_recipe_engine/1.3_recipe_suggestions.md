## 1. Problem Statement

Users forget items buried at the back of their freezer, causing safe food to silently expire and get discarded. This inflicts unnecessary cost on household budgets and generates preventable food waste. Feature 1.3 directly addresses this by implementing an automated expiration-aware query engine: a FastAPI route identifies all active `inventory_items` expiring within a configurable day window, constructs a ranked ingredient string, pipes it to the Spoonacular `findByIngredients` API to retrieve candidate recipes, persists the results to local `recipes` and `recipe_ingredients` tables via an upsert pattern, then forwards the top candidates through `gemini-1.5-flash` for safety validation and preference-aware ranking before returning a structured JSON response to the Flutter client.

---

## 2. Goals

- Execute a SQLAlchemy date-range query against `inventory_items` leveraging the `ix_inventory_items_expiration_date` index to retrieve expiring, unconsumed items without triggering a full table scan.
- Construct a Spoonacular-compatible ingredient string (sorted by earliest `expiration_date`, capped at 200 characters) and call `GET /recipes/findByIngredients` with `ranking=1` to maximize utilization of expiring stock.
- Persist each Spoonacular recipe to the local `recipes` table via a `spoonacular_id`-based existence check (upsert pattern), and write per-ingredient rows to `recipe_ingredients` linking matched ingredients back to their source `inventory_items.item_id`.
- Forward the top 5 candidate recipe titles and ingredient lists to `gemini-1.5-flash` for safety validation and ranked ordering, with graceful degradation if the Gemini API is unavailable.
- Return a fully typed HTTP `200 OK` response containing expiring items, Gemini-ranked recipes with per-recipe ingredient match breakdowns, and a `gemini_ranking_applied` boolean flag.

---

## 3. Non-Goals

- This feature does NOT implement ingredient ordering, grocery cart integration, or any external purchasing workflow.
- This feature does NOT persist user dietary preferences — the Gemini filter operates without preference context at this stage; a `user_preferences` table is planned for a future sprint.
- This feature does NOT support bulk recipe generation across multiple users in a single API call.
- This feature does NOT implement a recipe rating or feedback mechanism.

---

## 4. Personas & User Stories

- **As a User**, I want the app to show me recipes that use my chicken breasts expiring tomorrow so I can cook tonight instead of letting them go to waste.
- **As a Developer**, I want Spoonacular recipe results cached in the local `recipes` table so duplicate API calls for the same ingredient set do not consume daily quota.

## 5. Functional Requirements

- **FR-1.** The system MUST expose `GET /recipes/suggestions/{user_id}` accepting the path parameter `user_id: int` and the optional query parameter `days_window: int = Query(default=3, ge=1, le=14, description="Expiration lookahead window in days.")`. The route MUST be registered on a `recipes` `APIRouter` with `status_code=200`, `response_model=RecipeSuggestionsResponse`, and `tags=["Recipe Engine"]`.

- **FR-2.** The system MUST execute a SQLAlchemy query against `inventory_items` filtering rows where **all three** conditions are true: `expiration_date <= (date.today() + timedelta(days=days_window))`, `expiration_date >= date.today()`, and `is_consumed == False`. The query MUST use `.order_by(InventoryItem.expiration_date.asc())` to prioritize the most urgent items. The underlying MySQL execution plan MUST utilize the `ix_inventory_items_expiration_date` index (verified via `EXPLAIN SELECT ...` during integration testing — a full table scan on this query is a blocking defect).

- **FR-3.** If the filtered query returns zero rows, the system MUST return HTTP `200 OK` immediately with `{"user_id": user_id, "days_window": days_window, "items_expiring": [], "recipes": [], "gemini_ranking_applied": false, "message": "No items expiring within the selected window."}` without calling the Spoonacular API, the Gemini API, or writing to any database table.

- **FR-4.** The system MUST construct the Spoonacular ingredient string by joining `item.product_name` values (sorted ascending by `expiration_date`) with `","` separators. If the concatenated string exceeds **200 characters**, the system MUST truncate to the last complete ingredient name that keeps the total at or below 200 characters, prioritizing items with the earliest `expiration_date`. The truncated string MUST NOT end with a trailing comma or incomplete ingredient name.

- **FR-5.** The system MUST call `GET https://api.spoonacular.com/recipes/findByIngredients` via `httpx.AsyncClient(timeout=8.0)` with query parameters `ingredients={ingredient_string}`, `number=10`, `ranking=1` (maximize used ingredients — prioritizes recipes that consume more of the expiring stock), and `apiKey={settings.SPOONACULAR_API_KEY}`. If Spoonacular returns a non-2xx HTTP status, the system MUST raise `HTTPException(status_code=502, detail=f"Spoonacular API returned an unexpected status: {response.status_code}.")`. If `httpx.TimeoutException` is raised, the system MUST raise `HTTPException(status_code=504, detail="Spoonacular API request timed out.")`.

- **FR-6.** For each recipe object returned by Spoonacular, the system MUST check whether a row with the same `spoonacular_id` already exists in the `recipes` table via `db.query(Recipe).filter(Recipe.spoonacular_id == recipe["id"]).first()`. If no row exists, the system MUST insert a new `Recipe` row using `db.add()` and call `db.flush()` to retrieve the auto-assigned `recipe_id`. If a row already exists, the system MUST reuse the existing `recipe_id` and skip the insert. This upsert pattern MUST NOT issue a `db.commit()` until all recipe and ingredient rows for the batch have been staged.

- **FR-7.** For each recipe, the system MUST write one `RecipeIngredient` row per entry in the Spoonacular `usedIngredients` list and per entry in the `missedIngredients` list. For `usedIngredients` entries, the system MUST attempt to resolve an `item_id` by executing `db.query(InventoryItem).filter(func.lower(InventoryItem.product_name).contains(ingredient["name"].lower())).filter(InventoryItem.is_consumed == False).first()`. If a match is found, set `item_id` to the matched `InventoryItem.item_id` and `is_matched_to_inventory = True`. If no match is found, set `item_id = None` and `is_matched_to_inventory = False`. For `missedIngredients` entries, always set `item_id = None` and `is_matched_to_inventory = False`.

- **FR-8.** The system MUST forward the top **5** Spoonacular recipe titles and their `usedIngredients` lists to `gemini-1.5-flash` via `await model.generate_content_async([GEMINI_RANKING_PROMPT])` using the same `VISION_MODEL`-pattern established in Feature 1.2. The Gemini prompt MUST instruct the model to return a JSON array ranked by ingredient utilization efficiency and marked with a `gemini_safety_approved` boolean field. The model MUST be configured with `temperature=0.2, max_output_tokens=1024, response_mime_type="application/json"`.

- **FR-9.** If the Gemini API raises any exception during the ranking step (FR-8), the system MUST catch it, log at `WARNING` level (`f"Gemini ranking unavailable: {type(e).__name__}. Returning unranked Spoonacular results."`), set `gemini_ranking_applied = False` in the response body, and proceed with returning the raw Spoonacular results in their original order. The Gemini ranking step MUST NOT cause the overall endpoint to return a non-`200` status code under any circumstances.

- **FR-10.** After all `Recipe` and `RecipeIngredient` rows have been staged via `db.add()` and the Gemini ranking scores have been applied to the in-memory recipe objects, the system MUST call a single `db.commit()` to atomically persist all staged rows. If `db.commit()` raises `SQLAlchemyError`, the system MUST call `db.rollback()`, log the exception at `ERROR` level, and raise `HTTPException(status_code=500, detail="Database write failed during recipe caching. Please retry.")`.

## 6. Non-Functional Requirements

- **Performance:** The `ix_inventory_items_expiration_date` index MUST be present in the live schema and confirmed via `EXPLAIN` to be used by the FR-2 query — full table scan on this query is a blocking defect. The Spoonacular `httpx` client MUST have `timeout=8.0`. The overall endpoint MUST return within **15 seconds** end-to-end under normal network conditions.
- **Security:** `SPOONACULAR_API_KEY` MUST be loaded exclusively from `backend/.env` via `pydantic-settings`. It MUST NOT appear in log output, response bodies, or error detail strings. The key is passed as a query parameter to Spoonacular (their API design) — this MUST be acknowledged as a minor HTTPS-layer risk in the integration notes.
- **Observability:** Uvicorn MUST log: (1) the number of expiring items found and the `days_window` used, (2) the constructed ingredient string (safe to log), (3) the Spoonacular HTTP status and number of recipes returned, (4) whether Gemini ranking was applied, and (5) the total number of `Recipe` and `RecipeIngredient` rows committed.

## 7. Acceptance Criteria

- **AC-1.** Given an `inventory_items` row for `"Ribeye Steak"` with `expiration_date = date.today() + timedelta(days=1)` and `is_consumed = False`, when `GET /recipes/suggestions/1?days_window=3` is called, then the response has HTTP `200 OK`, `items_expiring` contains the steak entry with `days_until_expiry=1`, and `recipes` contains at least one steak-based recipe with `"ribeye steak"` or `"steak"` appearing in the `matched_ingredients` list.

- **AC-2.** Given an empty `inventory_items` table (or no items expiring within the window), when the endpoint is called, then HTTP `200 OK` is returned with `"items_expiring": []`, `"recipes": []`, and `"message": "No items expiring within the selected window."` — and zero external API calls are made.

- **AC-3.** Given Spoonacular returns HTTP `402` (quota exceeded), when the endpoint is called, then HTTP `502 Bad Gateway` is returned with the Spoonacular status code embedded in the `"detail"` field.

- **AC-4.** Given a successful Spoonacular call but the Gemini API raises `GoogleAPIError` during the ranking step, when the endpoint responds, then HTTP `200 OK` is returned with `"gemini_ranking_applied": false`, the recipes array is populated from raw Spoonacular results, and a `WARNING` line appears in Uvicorn stdout.

- **AC-5.** Given a successful full run (expiring items found → Spoonacular recipes → Gemini ranking applied), when the response is committed, then the `recipes` table in `fp-mysql` contains rows for each returned recipe (no duplicates on repeated calls with the same ingredients), and `recipe_ingredients` contains rows for both matched and unmatched ingredients with `is_matched_to_inventory` set correctly.

### Table: `recipes` — Write Target (Upsert Pattern)

```python
# backend/app/models/recipe.py
from sqlalchemy import (
    Integer, VARCHAR, TEXT, SmallInteger, Boolean,
    DateTime, Index, UniqueConstraint, func
)
from sqlalchemy.orm import Mapped, mapped_column, relationship
from typing import Optional, TYPE_CHECKING
from datetime import datetime
from app.db.base import Base

if TYPE_CHECKING:
    from app.models.recipe_ingredient import RecipeIngredient


class Recipe(Base):
    __tablename__ = "recipes"

    recipe_id: Mapped[int] = mapped_column(
        Integer, primary_key=True, autoincrement=True
    )
    spoonacular_id: Mapped[int] = mapped_column(
        Integer, nullable=False, unique=True  # Unique constraint enables upsert existence check
    )
    title: Mapped[str] = mapped_column(VARCHAR(500), nullable=False)
    image_url: Mapped[Optional[str]] = mapped_column(TEXT, nullable=True)
    source_url: Mapped[Optional[str]] = mapped_column(TEXT, nullable=True)
    ready_in_minutes: Mapped[Optional[int]] = mapped_column(SmallInteger, nullable=True)
    servings: Mapped[Optional[int]] = mapped_column(SmallInteger, nullable=True)
    gemini_safety_approved: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    gemini_rank: Mapped[Optional[int]] = mapped_column(SmallInteger, nullable=True)  # 1 = most suitable
    cached_at: Mapped[datetime] = mapped_column(
        DateTime, server_default=func.current_timestamp(), nullable=False
    )

    ingredients: Mapped[list["RecipeIngredient"]] = relationship(
        "RecipeIngredient",
        back_populates="recipe",
        cascade="all, delete-orphan"
    )

    __table_args__ = (
        Index("ix_recipes_spoonacular_id", "spoonacular_id", unique=True),
        Index("ix_recipes_gemini_rank", "gemini_rank"),
    )
```

### Table: `recipe_ingredients` — Write Target (Join Table)

```python
# backend/app/models/recipe_ingredient.py
from sqlalchemy import (
    Integer, VARCHAR, Boolean, ForeignKey, Index
)
from sqlalchemy.orm import Mapped, mapped_column, relationship
from typing import Optional, TYPE_CHECKING
from app.db.base import Base

if TYPE_CHECKING:
    from app.models.recipe import Recipe
    from app.models.inventory import InventoryItem


class RecipeIngredient(Base):
    __tablename__ = "recipe_ingredients"

    id: Mapped[int] = mapped_column(
        Integer, primary_key=True, autoincrement=True
    )
    recipe_id: Mapped[int] = mapped_column(
        Integer,
        ForeignKey("recipes.recipe_id", ondelete="CASCADE"),  # Orphaned ingredients are meaningless
        nullable=False
    )
    item_id: Mapped[Optional[int]] = mapped_column(
        Integer,
        ForeignKey("inventory_items.item_id", ondelete="SET NULL"),  # Preserve match record if item consumed
        nullable=True
    )
    ingredient_name: Mapped[str] = mapped_column(VARCHAR(255), nullable=False)       # From Spoonacular response
    spoonacular_ingredient_id: Mapped[Optional[int]] = mapped_column(Integer, nullable=True)
    is_matched_to_inventory: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)

    recipe: Mapped["Recipe"] = relationship("Recipe", back_populates="ingredients")
    inventory_item: Mapped[Optional["InventoryItem"]] = relationship("InventoryItem")

    __table_args__ = (
        Index("ix_recipe_ingredients_recipe_id", "recipe_id"),
        Index("ix_recipe_ingredients_item_id", "item_id"),
        Index("ix_recipe_ingredients_is_matched", "is_matched_to_inventory"),
    )
```

**Key Constraints:**
- `recipes.spoonacular_id` carries a `UNIQUE` constraint — this is the existence check key for the upsert pattern in FR-6.
- `recipe_ingredients.recipe_id` uses `ondelete="CASCADE"` — ingredient rows are deleted if their parent recipe is deleted.
- `recipe_ingredients.item_id` uses `ondelete="SET NULL"` — the ingredient match record persists even if the linked `inventory_items` row is consumed or deleted.
- All PKs are isolated auto-increment (`recipe_id`, `id`). No composite keys.

from pydantic import BaseModel, Field, ConfigDict
from typing import Optional
from datetime import date


class ExpiringItemSummary(BaseModel):
    """One expiring inventory item included in the response summary."""
    model_config = ConfigDict(from_attributes=True)

    item_id: int
    product_name: str
    expiration_date: date
    days_until_expiry: int = Field(
        ...,
        ge=0,
        description="Calendar days between today and expiration_date. 0 = expires today."
    )


class RecipeIngredientMatch(BaseModel):
    """Per-ingredient match detail for a given recipe."""
    model_config = ConfigDict(from_attributes=True)

    ingredient_name: str
    matched_item_id: Optional[int]          # FK to inventory_items.item_id; None if unmatched
    is_matched_to_inventory: bool


class RecipeSuggestion(BaseModel):
    """One Spoonacular recipe enriched with Gemini ranking and inventory match data."""
    model_config = ConfigDict(from_attributes=True)

    recipe_id: int                          # Local recipes.recipe_id (auto-assigned)
    spoonacular_id: int
    title: str
    image_url: Optional[str]
    ready_in_minutes: Optional[int]
    servings: Optional[int]
    gemini_rank: Optional[int]              # None if gemini_ranking_applied=False
    gemini_safety_approved: bool
    matched_ingredients: list[RecipeIngredientMatch]


class RecipeSuggestionsResponse(BaseModel):
    """HTTP 200 response — full structured output of the recipe engine."""
    user_id: int
    days_window: int
    items_expiring: list[ExpiringItemSummary]
    recipes: list[RecipeSuggestion]
    gemini_ranking_applied: bool
    message: Optional[str] = None           # Populated only when items_expiring is empty


# Internal schema — validates raw Gemini ranking JSON response
class GeminiRankedRecipe(BaseModel):
    model_config = ConfigDict(strict=True)

    spoonacular_id: int
    title: str
    gemini_rank: int = Field(..., ge=1)
    gemini_safety_approved: bool
    ranking_rationale: Optional[str] = Field(None, max_length=200)

## 11. AI / ML Considerations

**Model:** `gemini-1.5-flash`
**SDK:** `google-generativeai` (same instance configured by Feature 1.2's `configure_gemini()` startup call)

**Ranking Model Configuration:**
```python
RANKING_MODEL = genai.GenerativeModel(
    model_name="gemini-1.5-flash",
    generation_config=genai.GenerationConfig(
        temperature=0.2,          # Slightly higher than vision model; ranking benefits from mild creativity
        max_output_tokens=1024,   # Up to 5 ranked recipe objects with rationale
        response_mime_type="application/json",
    ),
)
```

**Gemini Ranking Prompt (verbatim constant — stored in `backend/app/services/recipe_ranker.py`):**
```
You are a dietary safety filter and meal planning assistant for a home freezer inventory app called Freezer Penguin.
Your task is to rank the following candidate recipes by their suitability for the provided expiring ingredients.

Expiring ingredients (sorted by urgency): {ingredient_list}

Candidate recipes from Spoonacular:
{recipe_json_array}

Return ONLY a valid JSON array — no markdown fences, no preamble, no explanations.
Each element MUST conform to this exact schema:
[
  {
    "spoonacular_id": <int: the recipe's Spoonacular ID>,
    "title": "<string>",
    "gemini_rank": <int: 1 = most suitable, ascending, no ties>,
    "gemini_safety_approved": <bool: false ONLY if the recipe requires raw/undercooked thawed proteins>,
    "ranking_rationale": "<string: one-sentence rationale, max 200 chars>"
  }
]

Ranking priority rules (in order):
1. Recipes that use the highest number of the provided expiring ingredients rank highest.
2. Recipes with shorter ready_in_minutes rank higher when ingredient counts are equal.
3. Mark gemini_safety_approved=false for any recipe requiring raw/undercooked seafood, eggs, or poultry.
```

**Fallback Strategy:**
- Gemini API unavailable → set `gemini_ranking_applied = False`, return raw Spoonacular order, HTTP `200` (FR-9).
- Gemini returns invalid JSON → log `WARNING`, fall back to unranked results.
- Empty Spoonacular result → return early with empty arrays before calling Gemini (FR-3).

## 12. Integration Points

- **Spoonacular Recipe API (External)**
  - Endpoint: `GET https://api.spoonacular.com/recipes/findByIngredients`
  - Key parameters: `ingredients` (comma-separated string), `number=10`, `ranking=1` (maximize used ingredients), `apiKey={settings.SPOONACULAR_API_KEY}`
  - Client: `httpx.AsyncClient(timeout=8.0)`
  - Response fields used: `id` → `spoonacular_id`, `title`, `image`, `usedIngredients[].name`, `usedIngredients[].id`, `missedIngredients[].name`, `missedIngredients[].id`
  - Free tier quota: **150 API calls/day**. At scale, recipe results cached in local `recipes` table to avoid re-querying for identical ingredient strings.
  - Key env var: `SPOONACULAR_API_KEY` in `backend/.env`

- **Google GenAI SDK (External)**
  - Reuses `RANKING_MODEL` configured by Feature 1.2's startup call. No additional SDK configuration required.
  - Gemini is invoked **after** Spoonacular results are cached to DB — Gemini failure does not block recipe delivery.

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Spoonacular free tier quota (150 calls/day) exhausted in development | High | Medium | Cache every Spoonacular response in the `recipes` table. Subsequent calls for identical ingredient strings query the local DB instead of Spoonacular (future optimization sprint). |
| `ix_inventory_items_expiration_date` index missing from live schema — full table scan on FR-2 query | Medium | High | Confirm index existence via `SHOW INDEX FROM inventory_items` before shipping. If absent, add via Alembic migration. Blocking defect if unresolved. |
| Spoonacular ingredient matching is fuzzy — `"ribeye steak"` in Spoonacular may not fuzzy-match `"Ribeye Steak"` in `inventory_items.product_name` | High | Low | FR-7 uses case-insensitive `LIKE`/`contains()` query. Future sprint can add synonym normalization via a lookup table. |
| Gemini ranking JSON does not include all 5 candidate `spoonacular_id` values | Medium | Low | Validate `GeminiRankedRecipe` array length before applying to response. Unranked recipes default to `gemini_rank=None` and `gemini_safety_approved=False`. |
| Multiple concurrent requests for the same user create duplicate `recipe_ingredients` rows | Low | Medium | The upsert existence check in FR-6 prevents duplicate `recipes` rows. For `recipe_ingredients`, add a composite unique constraint `(recipe_id, ingredient_name)` in a follow-up migration. |

## 18. Open Questions

- **Q1:** Should the recipe engine prioritize clearing the highest count of expiring items per recipe, or maximize the estimated dollar value of expiring items consumed? The current implementation uses Gemini to rank by ingredient count (FR-8 rule 1). A cost-value optimization would require a `purchase_price` column on `inventory_items` (not currently in scope).
- **Q2:** The live schema references a `recipe_ingredients_has_recipes` join table in the test plan. Is this a separate entity from `recipe_ingredients`, or is it the same table under a legacy name? If the table already exists with a different name, the ORM model in Section 8 must be adjusted to use `__tablename__ = "recipe_ingredients_has_recipes"` before running migrations.
- **Q3:** Should Spoonacular results be re-fetched after a configurable TTL (e.g., 7 days based on `recipes.cached_at`) to pick up newly available recipes for the same ingredient set, or is the cache permanent for the lifecycle of the application?
- **Q4:** At what Spoonacular daily quota threshold should the system begin serving exclusively from the local `recipes` cache? At 150 calls/day free tier, a moderate user base will exhaust this within hours. Should a Redis-based rate limiter be introduced before this feature ships to production?
