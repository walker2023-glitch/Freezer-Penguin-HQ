# 0.1 — Apartment-First Shared Household Food Inventory

> Implementation plan for the first useful Freezer Penguin proof of concept.
> This plan narrows the immediate goal to one apartment while preserving a
> clean path to more households and eventual app-store distribution.

## 1. Problem Statement

Freezer Penguin currently has attractive Flutter screens and a partially working
FastAPI inventory path, but it is not yet a trustworthy shared household tool.
Authentication returns a token that is not enforced, inventory requests accept a
client-supplied user ID, the consume action is mocked, and the app uses hardcoded
local URLs and preview data. The first business outcome is a reliable two-phone
household inventory: both roommates see the same source of truth, and a change
made by one person is visible to the other without mixing data between households.

This is an apartment proof of concept, not a premature public launch. Hosting,
database, and AI-cost changes should be made only when the current workflow or
security model requires them.

## 2. Goals

- Make two real users able to register/sign in from separate phones.
- Let them join one household and share one inventory source of truth.
- Support the complete core loop: add item, view item, update quantity, use item,
  and observe the result from the other phone.
- Enforce authentication and household authorization at every inventory route;
  never trust a user or household ID supplied by the client.
- Make the API address configurable so development phones can use a LAN or
  Tailscale address without code edits.
- Establish a fast, evidence-based QA workflow with executable finish conditions,
  automated API coverage, and a small real-device acceptance test.
- Preserve the existing Python/FastAPI, SQLAlchemy, MySQL, Flutter, and visual
  design investments so the prototype can later become a multi-household app.

## 3. Non-Goals

- No public hosting migration, database migration, or app-store submission yet.
- No payment, subscriptions, social features, or public household discovery.
- No offline-first synchronization or conflict-free replicated data model in this
  milestone; the server remains the source of truth.
- No automatic grocery ordering or retailer integration.
- No attempt to perfect AI recipe or vision quality before the inventory loop is
  reliable.
- No removal of existing feature plans. The barcode, vision, and recipe plans
  remain useful downstream references and must be reconciled with this plan.

## 4. Personas & User Stories

- **As the primary roommate**, I want to create a household and invite another
  roommate so that our food list is shared without sharing passwords.
- **As a roommate**, I want to see the current inventory from my own phone so I
  know what is available before shopping.
- **As either roommate**, I want to add an item with quantity and expiration so
  the household has useful, actionable data.
- **As either roommate**, I want to use one or more units of an item so the
  quantity reflects reality and the other phone sees the change.
- **As a future household owner**, I want membership checks and audit-friendly
  operations so adding more households does not create cross-household leaks.
- **As the developer/QA owner**, I want every claimed feature to have a runnable
  acceptance check and evidence of what was tested.

## 5. Functional Requirements

- **FR-1.** The backend MUST authenticate protected requests using a token that
  is issued at login and validated server-side.
- **FR-2.** Protected inventory routes MUST derive the current user from the
  authenticated request; they MUST NOT accept a trusted `user_id` query/path
  parameter from the client.
- **FR-3.** The data model MUST introduce a household entity and membership
  relation with an explicit owner/member role.
- **FR-4.** Every inventory item MUST belong to exactly one household after the
  household migration, either directly or through a server-resolved ownership
  relation.
- **FR-5.** A user MUST be able to create one household and generate a short-lived
  or revocable invite code for another user.
- **FR-6.** A user MUST be able to accept an invite only once and only become a
  member of the selected household.
- **FR-7.** Inventory reads MUST return only items in households where the current
  user has membership.
- **FR-8.** Inventory writes MUST reject unauthenticated users and users who are
  not members of the target household.
- **FR-9.** Manual item creation MUST support name, positive quantity, storage
  location, and optional expiration date. UPC MUST remain nullable for leftovers.
- **FR-10.** Updating quantity MUST be atomic and MUST reject negative quantities.
- **FR-11.** “Use item” MUST perform a real server-side mutation, record the
  resulting quantity, and remove/archive the row when quantity reaches zero.
- **FR-12.** Concurrent updates MUST not silently overwrite a newer quantity;
  the implementation MUST use an atomic update, transaction, or version check.
- **FR-13.** Flutter MUST send the bearer token on protected API calls and MUST
  refresh the visible inventory from the API after a successful mutation.
- **FR-14.** Flutter MUST accept a build-time API base URL override, for example
  `--dart-define=FREEZER_PENGUIN_API_URL=http://<reachable-host>:8000/api/v1`.
- **FR-15.** Preview/mock mode MUST be clearly labeled and MUST NOT be treated as
  evidence that the shared-household acceptance scenario works.
- **FR-16.** Barcode/photo/recipe features MAY be added only after the core
  household acceptance scenario passes.

## 6. Non-Functional Requirements

- **Performance** — Core authenticated inventory reads/writes SHOULD reach p95
  below 500 ms on the apartment LAN/Tailscale path, excluding external barcode
  or AI calls. Inventory queries MUST use indexed household/member filters.
- **Security** — Passwords MUST remain hashed. Tokens MUST be signed or stored
  server-side with expiration and revocation support. Secrets MUST come from
  environment configuration. Authorization MUST be tested for both same-household
  access and cross-household denial. Logs MUST NOT contain passwords or bearer
  tokens.
- **Privacy** — Household inventory is private by default. Invite codes MUST be
  scoped, expiring, and non-guessable enough for the apartment POC. Uploaded
  food photos MUST not be retained longer than needed unless the user explicitly
  chooses to save them.
- **Reliability** — Inventory writes MUST be transactional and idempotent where
  practical. The API MUST return actionable 401/403/404/409 errors rather than
  silently falling back to mock data.
- **Observability** — Logs SHOULD identify request type, authenticated user ID,
  household ID, item ID, status, and duration, while excluding credentials and
  sensitive payloads.
- **Maintainability** — Keep route, schema, model, and service boundaries clear;
  do not create a second database or parallel source of truth for the POC.
- **Backward compatibility** — Existing inventory rows MUST be assigned to a
  documented initial household during migration, or the migration MUST fail
  safely with a clear repair instruction.

## 7. Acceptance Criteria

- **AC-1.** *Given* two new accounts, *when* both users sign in on separate
  devices, *then* each receives a valid authenticated session and the app does
  not enter preview mode.
- **AC-2.** *Given* User A creates household H and invites User B, *when* User B
  accepts the invite, *then* both users are members of H and neither can see an
  unrelated household.
- **AC-3.** *Given* both users are members of H, *when* User A adds “Milk” with
  quantity 2 and an expiration date, *then* the item is persisted under H and
  appears on both phones after refresh.
- **AC-4.** *Given* the milk quantity is 2, *when* User B uses one, *then* the
  server stores quantity 1 and User A sees quantity 1 after refresh.
- **AC-5.** *Given* User C belongs to household X, *when* User C requests or
  mutates H’s inventory using guessed IDs, *then* the API returns 403/404 and no
  H data changes.
- **AC-6.** *Given* an expired or invalid token, *when* a protected route is
  called, *then* the API returns 401 and does not query or mutate inventory.
- **AC-7.** *Given* the API is started on a reachable LAN/Tailscale address,
  *when* two physical phones are built with that address, *then* both can sign
  in and complete AC-3 and AC-4 without changing source code.
- **AC-8.** *Given* the backend or network is unavailable, *when* a user tries
  to add or use an item, *then* the app shows a failure state and does not claim
  the operation succeeded.
- **AC-9.** *Given* the automated test suite and the two-phone checklist pass,
  *when* the milestone is reviewed, *then* the branch contains test evidence,
  migration notes, and a list of known unfinished work.

## 8. Data Model

Prefer additive SQL migrations over destructive changes. The exact existing
MySQL DDL must be confirmed before applying them.

### Proposed tables

- `households`: `household_id`, `name`, `created_by`, `created_at`, timestamps.
- `household_members`: `household_id`, `user_id`, `role`, `joined_at`, optional
  `revoked_at`; unique constraint on `(household_id, user_id)`.
- `household_invites`: `invite_id`, `household_id`, creator, hashed invite code,
  expiration, use status, created/accepted timestamps.

### Inventory changes

- Add `household_id` to `inventory_items` with a non-null foreign key after
  backfill, or use a carefully documented compatibility view during migration.
- Add indexes for `(household_id, expiration_date)` and
  `(household_id, item_id)`.
- Preserve nullable `UPC` and the current application-level single-column item
  identity rule from `SKILL.md`/`.cursorrules`.
- Preserve existing location/unit references unless the current schema proves
  they are unusable for household inventory.

### Migration/backfill

1. Create an initial apartment household for the existing owner.
2. Add that household ID to existing inventory rows.
3. Add the existing owner as an owner member.
4. Verify row counts and foreign keys.
5. Make `household_id` required only after verification.
6. Keep a rollback path that restores the previous nullable column state.

## 9. API Surface

All protected routes require `Authorization: Bearer <token>`.

- `POST /api/v1/auth/register` — create account.
- `POST /api/v1/auth/login` — issue expiring authenticated session.
- `GET /api/v1/me` — return authenticated user and active household summary.
- `POST /api/v1/households` — create household; creator becomes owner.
- `GET /api/v1/households` — list current memberships.
- `POST /api/v1/households/{household_id}/invites` — owner creates invite.
- `POST /api/v1/household-invites/{code}/accept` — authenticated user joins.
- `GET /api/v1/inventory` — list inventory for a selected/current household;
  household selection MUST be server-authorized.
- `POST /api/v1/inventory` — create a manual item.
- `PATCH /api/v1/inventory/{item_id}` — update allowed fields after membership
  check.
- `POST /api/v1/inventory/{item_id}/use` — decrement quantity atomically.
- `DELETE /api/v1/inventory/{item_id}` — optional owner/member-authorized delete.

The old `user_id=...` inventory contract MUST be deprecated and removed after
the mobile client is migrated. Analytics, recipes, barcode, and vision routes
must use the same authenticated household resolver before they are exposed as
shared features.

## 10. UI / UX

1. Keep the current Freezer Penguin visual identity and Flutter navigation.
2. Replace the current hardcoded user ID with authenticated session state.
3. Add a minimal household setup screen after first sign-in:
   - create household, or
   - enter invite code.
4. Show the active household name in the app shell.
5. Add a real “Add item” form with name, quantity, location, and expiration.
6. Add quantity controls and a clearly labeled “Use one” action.
7. After each mutation, show loading → success/error and refresh from the API.
8. Keep offline preview available for design work, but label it as preview and
   do not mix its data with authenticated data.
9. Include empty, loading, unauthorized, unavailable, duplicate, and conflict
   states. All new user-facing text must use Flutter localization resources.
10. Verify the flow on a small Android phone and a second physical device before
    considering the milestone complete.

## 11. AI / ML Considerations

AI is intentionally downstream of the household inventory foundation.

- Barcode intake should prefer Open Food Facts/cache data and remain useful when
  the external API is unavailable.
- Photo intake should show the inferred name, quantity, and expiration for user
  confirmation before committing uncertain results.
- Vision calls need payload limits, timeout handling, confidence thresholds,
  audit records, and a non-AI manual fallback.
- Recipe suggestions should be generated from the authenticated household’s
  inventory only; they must never receive another household’s items.
- External API calls need explicit timeouts, bounded payloads, caching, and a
  cost budget before they are enabled for wider use.

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Existing token is not actually validated | H | H | Implement auth dependency and 401 tests before adding household UI |
| Inventory rows have no household owner | H | H | Add migration/backfill and verify counts before enforcing NOT NULL |
| Two clients overwrite quantity | M | H | Use atomic decrement/version checks and concurrency tests |
| Tailscale/LAN address is unreachable from phones | H | H | Add configurable URL, health check, device checklist, and explicit network docs |
| Preview data is mistaken for live data | H | M | Label preview, separate code path, and exclude preview from acceptance evidence |
| External AI/API cost or latency dominates UX | M | M | Keep manual path first; cache, time out, cap payloads, and measure p95 |
| Existing analytics/recipe routes leak by user ID | H | H | Apply the same household resolver before enabling those screens for real users |
| Migration damages existing data | M | H | Backup, additive migration, row-count verification, rollback script |
| Agents make broad unreviewed changes | M | H | One change owner, small branches, executable finish conditions, independent review |

## 15. Rollout Plan

- Branch each milestone from the latest verified `main`.
- Land schema migrations before code that requires them.
- Keep the apartment POC behind a development configuration; do not expose the
  database publicly.
- Dogfood with Dallas plus one roommate using two real phones and one household.
- Roll back by disabling the new household flow, restoring the database backup,
  and reverting the additive migration if verification fails.
- Declare the POC complete only when AC-1 through AC-9 are evidenced.
- Do not begin public hosting/app-store work until the core flow is stable for a
  short period of real household use.

## 16. Test Plan

The QA approach follows the referenced poteto/pstack principle: an agent or
developer is not finished when code exists; they are finished when the definition
of done is executable, the real artifact has been verified, and evidence is left
behind. Prefer several small, independently verifiable jobs over one large
feature request.

### Test layers

- **Unit** — token creation/validation, invite hashing/expiry, quantity rules,
  household authorization helpers, schema validation.
- **Integration** — FastAPI routes against an isolated test database; registration,
  login, household creation/join, inventory CRUD, and transaction rollback.
- **Security** — missing/expired/tampered token; guessed user/household/item IDs;
  cross-household reads; cross-household writes; invite reuse/expiry; SQL/API
  validation; logs without credentials.
- **Contract** — OpenAPI response shapes, status codes, Flutter request headers,
  and configurable API URL behavior.
- **Mobile** — Flutter widget tests for auth gate, household setup, add/use states,
  error handling, and preview/live separation.
- **Real-device acceptance** — two physical phones on the same reachable network.
- **Performance** — measure core API p50/p95 with a small seeded household; do not
  optimize external AI calls before core timings are known.
- **Exploratory** — airplane mode, server restart, duplicate taps, rapid refresh,
  expired item, quantity 1 → use, quantity 0 rejection, rotation/backgrounding,
  and a second household with similar item names.

### Required evidence per change

1. Exact finish condition written before implementation.
2. Test command(s) and environment recorded.
3. Passing output or a reproducible failure captured.
4. Files/routes/schema affected listed.
5. Remaining uncertainty and next unfinished part stated.

### Two-phone acceptance checklist

1. Start backend on a known LAN/Tailscale address and verify `/` health endpoint.
2. Build Phone A and Phone B with the same `FREEZER_PENGUIN_API_URL`.
3. Register two distinct accounts.
4. Create household on Phone A; accept invite on Phone B.
5. Add “Milk”, quantity 2, expiration date on Phone A.
6. Refresh Phone B and verify the same item/quantity/date.
7. Use one milk on Phone B.
8. Refresh Phone A and verify quantity 1.
9. Create a separate household/user and verify no access to the first household.
10. Stop/restart the API, repeat a read, and verify the source of truth remains the
    database rather than local/mock state.
11. Record device models, OS versions, network path, commit SHA, commands,
    screenshots/logs, and any failures.

## 18. Open Questions

1. Should a user belong to multiple households, or exactly one for the apartment
   POC? Design the schema for multiple memberships even if the first UI selects
   one active household.
2. Should “use item” decrement one unit or allow an arbitrary quantity entry?
3. Should zero-quantity items be archived for waste/consumption analytics or
   deleted from active inventory?
4. Which roommate account should own the first migrated inventory rows?
5. Is Tailscale sufficient for the apartment pilot, or should a small HTTPS API
   be used before a second physical location is tested?
6. What token/session mechanism is acceptable for the POC while keeping a clear
   upgrade path to production JWT/session storage?
7. Which existing analytics screens are still intentionally mock-only, and when
   should they be hidden from live users?
